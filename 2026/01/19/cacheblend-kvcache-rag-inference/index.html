CacheBlend：RAG 场景下的 KV Cache 复用技术调研

CacheBlend 的核心思想是：”积木式”复用 KV Cache。

在 RAG 场景中，我们将检索到的1个或多个文档拼接成一个长 Prompt 输入给模型。传统的做法是每次都要重新计算整个 Prompt 的 KV Cache，这会导致 TTFT 非常高。CacheBlend 允许我们直接把预先计算好的文档 KV Cache Blend 在一起，通过算法修正位置编码带来的差异，从而跳过繁重的 Prefill 计算阶段。

以下是详细的技术原理解析：

1. 核心痛点：位置编码的动态性

在 Transformer 架构（特别是使用 RoPE 旋转位置编码的模型，如 LLaMA, Qwen）中，KV Cache 是位置敏感的。

  • 场景：
    • 离线计算了文档 A 的 KV Cache，当时假设它是从第 0 个 token 开始的。
    • 但是在线推理时，文档 A 被拼接在 Prompt 的中间（例如从第 500 个 token 开始）。
  • 问题：
    • 在线推理时，无论 CacheBlend 还是 GistToken 方案都存在需要调整拼接的 KVCache 所在位置的问题。
  • 冲突：
    • 由于 RoPE 的特性，Token_i 在位置 0 生成的 Key/Value 向量，与在位置 500 生成的 Key/Value 向量是完全不同的。不能直接把离线的 KV Cache 搬过来用。

2. CacheBlend 的核心机制：Selective KV Recomputation

CacheBlend 的核心创新在于 Selective KV Recomputation（选择性 KV 重算），它打破了传统 KV Cache 必须前缀匹配的限制。

A. 预计算与非前缀 KV 复用

  • 机制：CacheBlend 允许复用任何预计算好 text chunks 的 KV Cache，即使它们在新的 Prompt 中不是从开头开始（非前缀）。
  • 挑战：直接拼接会导致由于位置编码（RoPE）和交叉注意力（Cross-Attention）缺失带来的精度下降。

B. Selective KV Recomputation (选择性重算)

为了解决精度问题，CacheBlend 并不重算所有 Token，而是识别并重算少量关键 Token：

  1. High-KV-Deviation (HKVD) Token 识别：CacheBlend 发现只有少部分 Token（约 5-18%）的 KV 值受上下文影响巨大。这些通常是 attention sinks 或具有强语义依赖的 token。
  2. 重算策略：
    • 对于大部分 Token：直接复用预存的 KV Cache（配合必要的位置编码调整）。
    • 对于 HKVD Token：使用当前的完整上下文重新计算其 KV 值。
  • 效果：通过仅重算 ~15% 的 Token，CacheBlend 在保持 generation quality (F1/Rouge-L 损失 < 0.03) 的同时，大幅减少了计算量。

C. Pipelining (流水线并行)

CacheBlend 进一步优化了系统延迟：

  • IO 与计算重叠：在从较慢的存储介质（如 CPU 内存或 SSD）加载 KV Cache 的同时，GPU 开始并行进行 HKVD Token 的重算。
  • Latency Hiding：由于重算只需要很小的计算量，这部分时间往往可以被 KV Cache 的传输时间所掩盖（Hiding Latency），从而实现”零开销”的修正。

D. 修正注意力 (Correcting Attention)

简单的拼接可能会导致注意力分布出现断层。CacheBlend 会在后续的 Attention 计算阶段引入一个 Bias 或者平滑系数，来模拟完整 Forward Pass 下的注意力分布，确保模型不会因为拼接而”读不懂”上下文。

3. 系统集成与性能

  • 集成：CacheBlend 已集成在 LMCache 开源项目中，并深入整合进 vLLM Production Stack。
    • KvawareRouter：vLLM production stack 实现了 KvawareRouter，能够基于 KV Cache 的分布情况智能路由请求，充分利用 CacheBlend 的能力。
    • 版本支持：支持 vLLM v1 及其生产栈（支持 KV offloading, disaggregated prefill 等特性）。
  • 性能数据：
    • TTFT (Time-To-First-Token)：降低 2.2x - 3.3x。
    • Throughput (吞吐量)：提升 2.8x - 5x。
    • 精度：相比全量重算，精度损失可忽略不计。

4. 与其他技术的对比

技术方案 原理 优势 劣势
标准推理 (Baseline) 每次实时计算所有 Token 的 KV 精度 100% 无损 TTFT 极高，显存带宽压力大
Prompt Cache (如 vLLM) 只能复用完全前缀匹配的 KV 实现简单，完全无损 必须前缀一致（Prefix Match）。RAG 中文档顺序一变就失效
CacheBlend 部分复用 + 位置修正 灵活。文档顺序可变，任意组合 存在微小的精度损失（通常 <1%），实现复杂度高
